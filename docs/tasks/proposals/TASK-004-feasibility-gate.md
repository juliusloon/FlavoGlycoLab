每个门必须记录：`gate`、`question`、`status`、`evidence_type`、`source_ref`、`verified_at`、`responsible_party`、`target_date`、`consequence_A`、`reusable_B`、`next_action`。
`status`限定为`verified / partial / blocked / unknown`；`unknown`和`blocked`不得混为同一事实；只有外部可核证凭据才可写`verified`。模型给出的推断须与人工回复、原文/回执分栏。

## 判定规则
| 输出 | 必要条件 | 后续操作 |
| --- | --- | --- |
| `GO_TO_PLAN` | F0已确认；F1、F2、F3、F4的最小可交付路径均有实证、负责人和可用时间，未发现不可逾越阻断 | 所有者可另行授权快线实施TASK；不视为系统/科研/安全已验收 |
| `CONDITIONAL` | F0已确认，但其余门部分仍待明确，存在具体责任人、证据获取方式和期限 | 限制新增特供工作；在截止前复审，不承诺按期申报 |
| `HOLD` | F0未知，或关键可达性缺责任方、缺可信时间线 | 暂停A轨不可复用工作；B轨按单独批准的TASK继续 |
| `NO_GO_2026` | 校内明确无资格，或无法在实际截止前取得关键数据/权利/平台安全/课程支持 | 关闭2026申报快线；不停止B轨，未来征集须重新核对政策 |

以上四项为**建议决策**；由所有者确认，不能把Agent判定变成院校批准。若10-17尚无校内结果，推荐`HOLD`而不是无依据的`NO_GO_2026`。
